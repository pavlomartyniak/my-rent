# Kolo API

REST API для мобільного застосунку: NestJS + MongoDB (Mongoose), автентифікація через JWT.

## Запуск

```bash
cd backend
cp .env.example .env      # і заповніть MONGODB_URI та JWT_SECRET
npm install
npm run start:dev         # http://localhost:4000
```

З кореня репозиторію: `npm run api`.

Змінні середовища (`.env`, у git не потрапляє):

| Змінна | Призначення |
|---|---|
| `PORT` | Порт API (за замовчуванням 3000; у проєкті 4000) |
| `MONGODB_URI` | Рядок підключення до MongoDB Atlas |
| `MONGODB_DB` | Назва бази (`my-rent`) |
| `JWT_SECRET` | Секрет підпису токенів, мінімум 32 символи (`openssl rand -base64 48`) |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | дані Cloudinary для завантаження фото авто; без них `POST /media/upload-signature` відповідає 503 |
| `DEMO_MODE` | `true` дозволяє перемикати Pro без оплати (поки не підключено оплату). **У продакшені — `false`** |

Мобільний застосунок бере адресу API з `EXPO_PUBLIC_API_URL` (файл `.env.local` у корені). На реальному
телефоні це IP комп'ютера в Wi-Fi, наприклад `http://192.168.1.10:4000`.

## Деплой на Render

Конфіг у [render.yaml](../render.yaml) (Blueprint). Кроки:

1. Запуште репозиторій на GitHub.
2. MongoDB Atlas → Network Access → дозвольте підключення з Render (`0.0.0.0/0`, якщо немає статичних IP).
3. Render → New → Blueprint → оберіть репозиторій. У запиті введіть `MONGODB_URI`.
4. Після деплою перевірте `https://<ваш-сервіс>.onrender.com/health`.
5. У мобільному застосунку задайте `EXPO_PUBLIC_API_URL=https://<ваш-сервіс>.onrender.com`.

На безкоштовному плані сервіс «засинає» після ~15 хв без запитів, перший запит після цього триває до хвилини.

## Ендпоінти

Усі, крім `/auth/*` і `/health`, вимагають заголовок `Authorization: Bearer <token>`.

**Типи акаунтів.** При реєстрації обирається `role`: `owner` (власник авто, за замовчуванням) або `renter` (орендар); потім вона не
змінюється. Власнику доступні облік, звіти, експорт, оголошення й вхідні запити; орендарю — пошук оголошень і свої запити.

## Звіти

Усі показники (прибуток, маржа, зміна до минулого періоду, ROI, окупність, рейтингові дані, витрати за категоріями)
рахує сервер за допомогою агрегацій MongoDB; клієнти лише показують відповіді. Тож будь-який новий клієнт
(вебверсія, інший застосунок) отримує ті самі числа без повторення правил. Правила розрахунків — чисті функції
в `src/reports/reports.math.ts`. Дати зберігаються рядками `YYYY-MM-DD`, тож фільтр за періодом — діапазон
рядків, що використовує індекс `{userId, date}`.

## Маркетплейс

Власник публікує вільне авто (місто, ціна за добу, опис), орендарі шукають за містом і ціною й надсилають запити на дати.
Телефони відкриваються обом сторонам лише після прийняття запиту; до того орендар бачить власника як «Ім'я П.».
Прийняття відбувається в одній транзакції MongoDB: оновлюється авто, запит, і відхиляються інші запити на це авто.
Орендар також може створити **заявку** «шукаю таке авто» (марка й модель необов'язкові, місто, дати, бюджет, побажання).
Власники бачать відкриті заявки й пропонують свої вільні авто; орендар приймає одну пропозицію, і авто так само автоматично
потрапляє в облік власника. Прийняття запиту на оренду чи пропозиції відхиляє решту запитів і пропозицій на це авто.
Фото завантажуються з телефона напряму в Cloudinary за підписом цього сервера, секрет не залишає сервер.

## Каталог марок і моделей

Дані лежать у `data/autoria-catalog.json` (зібрані з AUTO.RIA, легкові авто: ~390 марок, ~5000 моделей, ~10 000 поколінь
з роками випуску). Файл завантажується в пам'ять при старті, окрема база не потрібна. Щоб оновити каталог, замініть файл
і перезапустіть сервіс. Марки без моделей у відповідях не показуються. Українські назви марок для пошуку кирилицею
задані в `src/catalog/catalog.aliases.ts`.

## Безпека

- Паролі — bcrypt (12 раундів); токени — JWT на 30 днів.
- Ліміти запитів: 120/хв загалом, 10/хв на `/auth/*`.
- Валідація всіх вхідних даних (`class-validator`), невідомі поля відкидаються.
- `helmet` для HTTP-заголовків. CORS вимкнено (мобільному клієнту не потрібен).

## Відомі обмеження

- Фото авто: зберігається лише локальний `photoUri` з пристрою. Завантаження файлів не реалізоване.
- Токен не відкликається до завершення терміну (немає refresh-токенів).
- Автоматичні тести є лише для розрахунків звітів (`npm test`, `test/`); решта сценаріїв перевірялась вручну на живій базі.


## Чат у реальному часі (socket.io)

Підключення: `io(API_URL, { transports: ['websocket'], auth: { token } })` з тим самим JWT, що й для REST; без дійсного токена сервер відключає сокет.
Усі записи (повідомлення, «прочитано») йдуть через REST, а сокет лише доставляє події, тож чат працює і при тимчасовому обриві з'єднання (після повернення застосунок перезавантажує розмову).

| Подія | Напрямок | Дані |
|---|---|---|
| `message` | сервер → клієнт (обом сторонам, включно з іншими пристроями автора) | `conversationId`, `senderId`, `message`, `unread` |
| `read` | сервер → клієнт | `conversationId`, `by` (`owner`/`renter`), `at` |
| `typing` | клієнт → сервер → співрозмовнику | `conversationId` (не частіше за раз на 1,5 с) |
| `removed` | сервер → клієнт (пристрої того, хто видалив) | `conversationId` |

Ім'я співрозмовника в чаті скорочене («Олена Т.»), доки між людьми немає прийнятої домовленості чи оренди. Render підтримує WebSocket на звичайному web service.

## Життєвий цикл запитів, пропозицій і заявок

- Хто відхилив, скасував чи відкликав запит чи пропозицію, тому вони зникають зі списку одразу (`hiddenFor`); друга сторона бачить результат і може видалити його сама. Те саме з конкуруючими запитами й пропозиціями, які відхиляються автоматично, коли одну прийнято.
- Коли оренда з прийнятого запиту чи пропозиції розірвана (за згодою) або закінчилась за датою, вони стають `ended`, а в списках замість «Прийнято» видно етап оренди (`dealStage`). `ended`, `declined`, `cancelled`, `withdrawn` кожна сторона може видалити з `DELETE /rentals/:id` чи `/offers/:id`.
- Фоновий прохід (`LIFECYCLE_INTERVAL_MS`, за замовчуванням щогодини): завершує прийняті запити за закінченими орендами; видаляє виконані заявки через 30 днів після завершення оренди; видаляє розмови без активної домовленості, у яких 30 днів немає повідомлень.
- Індекси TTL у MongoDB видаляють скасовані, відхилені, відкликані й завершені запити, пропозиції та скасовані заявки через 30 днів.


## Договір і початок оренди

1. Власник приймає запит чи орендар — пропозицію: створюється оренда в статусі `awaiting` з договором (умови фіксуються й більше не змінюються), авто стає «Заброньоване».
2. Обидві сторони бачать і читають договір одразу після прийняття та можуть завантажити PDF, а **підписують його під час зустрічі**, коли передаються авто, ключі й гроші: підписання (`/deals/:id/sign`) відкривається за добу до початку оренди й триває ще 2 доби після неї (`signing` у відповіді). Підпис містить час, метод і ідентифікатор, прив'язаний до відбитку умов.
3. Коли підписали обидві сторони, оренда стає `active`: авто стає «В оренді» (якщо дата початку вже настала) або лишається «Заброньованим» до цієї дати. Облік (заробіток і витрати орендаря) відкривається лише після підписання.
4. Якщо договір не підписали, поки вікно підписання відкрите (до 2 діб після початку), фоновий прохід скасовує домовленість: авто знову вільне. До підписання кожна сторона може скасувати її сама.
5. Шрифт PDF: DejaVu Sans (`data/fonts`, вільна ліцензія Bitstream Vera).

## Автоповідомлення в чаті

Коли орендар надсилає запит чи власник — пропозицію, сервер одразу відкриває розмову й кидає перше повідомлення від імені автора (авто, дати, строк, сума, його примітка); у відповіді є `chatId`. Те саме при прийнятті: «Домовленість прийнято, договір сформовано, підписуємо при зустрічі». Збій чату не ламає сам запит.

## План оплати й підтвердження платежів

- У запиті (орендар) і пропозиції (власник) обирається план оплати: `lump` (вся сума одразу, за замовчуванням), `weekly` (від 8 діб, платіж наперед за кожні 7 діб, під ритм виплат таксі-агрегаторів) чи `daily` (від 2 діб, платіж наперед за кожну добу). Перший платіж у день передачі авто, останній на залишок. План, графік платежів і суми фіксуються в договорі. Старий `monthly` нових угод не приймає, але раніше укладені працюють далі. У нагадуваннях «ви сплатили?» для кожної угоди показується лише найстаріший невиплачений платіж.
- Облік не створюється при підписанні. Після підписання застосунок питає кожну сторону про поточний платіж: орендаря «ви сплатили?», власника «ви отримали?» (`GET /deals/awaiting-payment`). Відповідь `POST /deals/:id/payments/:n/confirm` (без суми — повна, з сумою — частина) створює чи оновлює запис в обліку цієї сторони: витрата «Оренда авто» в орендаря, дохід «Оренда» у власника. `POST .../later` відкладає запитання до завтра.
- Застава (гарантійний платіж) вказується на авто (`listing.deposit`), фіксується в запиті чи пропозиції, а при прийнятті — в договорі (`terms.deposit`, окремий пункт 3.4); у суму оренди й графік вона не входить. Це лише відмітка: орендар «вніс», власник «отримав» (`POST /deals/:id/deposit/confirm`, після підписання). Повернення й утримання сторони домовляються самі, в облік і звіти застава не потрапляє.
- Перший платіж доступний одразу після підписання (гроші передаються під час зустрічі), наступні — з дати платежу. Обидві сторони бачать, що підтвердила друга, і розбіжність сум.
- Розірвання: майбутні платежі, за які нічого не підтверджено, скасовуються; у відповіді оренди є `settlement` (належить за використані доби, підтверджено орендарем і власником).

## Живе оновлення списків (сокет)

Крім чату, сокет сповіщає про зміни, щоб запити, пропозиції, оренди й статус авто оновлювались без перезавантаження. Подія `changed` має `scopes` (`rentals`, `offers`, `wanted`, `deals`, `cars`) і містить лише сигнал, а не дані: застосунок сам перезавантажує відповідні списки. Сигнали йдуть другій стороні (і конкурентам, яким відмовлено) при створенні, прийнятті, відхиленні, скасуванні, підписанні, підтвердженні платежу, розірванні, а також при фоновому прибиранні. Опитування раз на 5 хвилин лишилось запасним каналом.


## Відновлення пароля

| Метод | Маршрут | Призначення |
|---|---|---|
| POST | `/auth/forgot` `{email}` | Надсилає 6-значний код (15 хв) на пошту; відповідь 204 однакова для відомих і невідомих адрес |
| POST | `/auth/reset` `{email, code, password}` | Змінює пароль і входить; після 5 невдалих спроб код анулюється |

Листи надсилає Resend (`RESEND_API_KEY`, `MAIL_FROM`); без ключа лист лише пишеться в журнал сервера.
